# Auditoria SEO profunda — WABOT / BOTinho

Data: 2026-05-15  
Escopo: dashboard Next.js público, páginas programáticas, blog/materiais, arquivos de descoberta (`robots.txt`, `sitemap.xml`, `llms.txt`, `pricing.md`) e riscos técnicos que podem afetar indexação, rastreamento, compartilhamento e conversão orgânica.

## Sumário executivo

O projeto já tem uma base orgânica acima da média para um MVP: há homepage, cluster de landing pages por cidade, páginas por nicho, hub de conteúdos, blog, materiais, sitemap dinâmico, robots dinâmico, `llms.txt`, `pricing.md`, canonicals em parte das páginas e JSON-LD em homepage/LPs/conteúdos. A arquitetura é boa para capturar demanda de fundo de funil em português do Brasil sobre automação de grupos, afiliados e WhatsApp.

A principal crítica é que o projeto ainda mistura sinais fortes com inconsistências técnicas que podem desperdiçar autoridade: canonicals herdados apontando páginas públicas para a home, títulos duplicando `| BOTinho`, páginas privadas/admin sem `noindex` HTML confiável, robots estático e dinâmico divergentes, `promo-vip-7dias` no sitemap apesar de bloqueado no robots, suporte com schema FAQ definido mas não renderizado, ausência de imagem social OG, descrições curtas/longas demais e muitas LPs programáticas com risco de conteúdo fino/parecido.

### Top 10 prioridades

1. **Corrigir canonicals herdados** em `/suporte`, `/quem-somos`, `/termos`, `/privacidade`, `/login`, `/promo-vip-7dias`, `/dashboard/*` e `/admin/*`.
2. **Adicionar `noindex` robusto** para `/dashboard/*`, `/admin/*`, `/api/*`, `/login` e páginas promocionais temporárias via metadata/layout server ou headers.
3. **Remover páginas bloqueadas do sitemap** ou liberar/canonizar adequadamente. O sitemap atual lista `/promo-vip-7dias`, enquanto o robots a bloqueia.
4. **Eliminar duplicação de marca nos titles** (`Suporte | BOTinho | BOTinho`, `Espelhar grupos... | BOTinho | BOTinho`).
5. **Sincronizar `dashboard/app/robots.js` e `dashboard/public/robots.txt`** para evitar comportamento diferente dependendo do arquivo servido.
6. **Renderizar o FAQ schema de suporte** ou remover a constante morta.
7. **Criar imagens OG/Twitter por cluster** e declarar `openGraph.images`/`twitter.images`.
8. **Revisar descrições**: homepage tem descrição muito longa; suporte/legal têm descrições curtas e pouco orientadas a intenção.
9. **Fortalecer diferencial e prova das LPs programáticas** para reduzir risco de doorway/thin content.
10. **Criar rotina de validação SEO no CI**: checar sitemap vs rotas, canonicals, noindex, titles duplicados, robots e presença mínima de metadata.

## Pontos fortes atuais

- **Arquitetura de cluster orgânico já existe**: homepage, hub `/conteudos`, blog, materiais, LPs por cidade e nicho.
- **Sitemap dinâmico centraliza as principais URLs públicas** e inclui `lastModified`, `changeFrequency` e `priority`.
- **Robots dinâmico bloqueia áreas sensíveis** como dashboard, admin e endpoints de auth/admin.
- **Homepage tem schema de Organization, SoftwareApplication e FAQPage**.
- **LPs programáticas têm FAQPage, HowTo e SoftwareApplication**.
- **Conteúdos editoriais usam Article/FAQ em parte das páginas**.
- **`metadataBase` está definido para o domínio de produção**, permitindo geração absoluta de canonicals e social tags.
- **`llms.txt` e `pricing.md` existem em `public/`**, o que é positivo para descoberta por agentes/LLMs e por compradores técnicos.

## Achados técnicos detalhados

### P0 — Canonicals herdados apontam várias páginas para a home

**Impacto:** alto. Canonical errado é um sinal forte para consolidar páginas diferentes na home, reduzindo chance de indexação individual de páginas importantes como suporte, legal, login e páginas internas. Em páginas privadas, o canonical para home também pode confundir relatórios de indexação.

**Evidência:** o layout raiz define `alternates: { canonical: '/' }`. Páginas sem canonical próprio herdam esse valor. No build local, `/suporte`, `/quem-somos`, `/termos`, `/privacidade`, `/login`, `/dashboard/inicio`, `/admin` e `/promo-vip-7dias` renderizaram canonical `https://espelhagrupos.com.br`.

**Recomendação:**

- Criar metadata por página pública institucional:
  - `/suporte` → canonical `/suporte`
  - `/quem-somos` → `/quem-somos`
  - `/termos` → `/termos`
  - `/privacidade` → `/privacidade`
- Para páginas privadas/promocionais temporárias, preferir `robots: { index: false, follow: false }` e canonical próprio ou nenhum canonical se a página não deve entrar no índice.
- Evitar canonical global no root layout quando muitas páginas precisam de canonical próprio; em Next, deixe o canonical na home e em cada page/layout relevante.

### P0 — Áreas privadas/admin dependem só de robots.txt para não aparecerem

**Impacto:** alto. `robots.txt` impede crawling, mas não garante remoção/indexação se a URL for descoberta por links externos ou históricos. Para páginas com sessão, admin e dashboard, o ideal é `noindex` renderizado ou header `X-Robots-Tag: noindex, nofollow`.

**Evidência:** `/dashboard/inicio`, `/dashboard` e `/admin` renderizaram título/description/canonical da home e não renderizaram `<meta name="robots" content="noindex...">`. Apenas `/login` e `/dashboard/planos` têm metadata `robots` própria.

**Recomendação:**

- Criar layouts server wrapper para `/dashboard` e `/admin` que exportem metadata `robots: { index: false, follow: false }` sem quebrar o layout client atual. Exemplo: separar `DashboardClientLayout` e deixar `dashboard/app/dashboard/layout.js` server com metadata + client child.
- Alternativa ainda mais forte: headers em `next.config.mjs` com `X-Robots-Tag: noindex, nofollow` para `/dashboard/:path*`, `/admin/:path*`, `/api/:path*` e `/login`.
- Validar em staging na porta 3006 antes de produção, porque mexer em layout do dashboard pode afetar autenticação/client state.

### P0 — Sitemap lista URL bloqueada no robots

**Impacto:** alto/médio. Sitemap deve conter apenas URLs canônicas e indexáveis. `/promo-vip-7dias` está em `CORE_ROUTES`, mas `robots.js` e `public/robots.txt` bloqueiam `/promo-vip-7dias`. Isso envia sinal contraditório: “indexe” pelo sitemap e “não rastreie” pelo robots.

**Recomendação:** escolher um caminho:

- Se `/promo-vip-7dias` é campanha temporária ou paga: remover do sitemap e adicionar `noindex`.
- Se deve rankear organicamente: remover o disallow, criar title/description/canonical próprios e conteúdo indexável diferenciado.

### P1 — `robots.js` e `public/robots.txt` divergem

**Impacto:** médio. Next gera `/robots.txt` pelo route metadata, mas a presença de um arquivo estático com regras diferentes aumenta risco operacional e confusão em deploy/cache/CDN.

**Divergências encontradas:**

- Dinâmico permite `/api/public/faq` e `/api/public/plans`; estático bloqueia `/api/*` inteiro.
- Dinâmico bloqueia `/api/admin/*`, `/api/auth/*`, `/api/dashboard/*`, `/api/payments/*`; estático bloqueia tudo em `/api/*`.
- Ambos bloqueiam `/promo-vip-7dias`, mas o sitemap inclui a URL.

**Recomendação:** manter uma única fonte canônica. Preferência: `dashboard/app/robots.js` por usar `getSiteUrl()` e acompanhar deploy. Remover o estático ou gerar o estático a partir da mesma lista.

### P1 — Duplicação de marca nos títulos

**Impacto:** médio. Titles longos e repetidos reduzem CTR, desperdiçam pixels e parecem menos profissionais. O root layout usa template `%s | BOTinho`, mas muitas páginas já incluem `| BOTinho` no próprio title.

**Evidência renderizada:**

- `/suporte`: `Suporte | BOTinho | BOTinho`
- `/quem-somos`: `Quem Somos | BOTinho | BOTinho`
- `/termos`: `Termos de Uso | BOTinho | BOTinho`
- `/privacidade`: `Política de Privacidade | BOTinho | BOTinho`
- `/bot-ofertas-restaurantes-whatsapp`: `Bot de ofertas para restaurantes no WhatsApp | BOTinho | BOTinho`
- `/espelhar-grupos-whatsapp-sao-paulo`: `Espelhar grupos WhatsApp em São Paulo | BOTinho | BOTinho`

**Recomendação:** padronizar: page titles **sem** `| BOTinho`; deixar o template global aplicar a marca. Exceção: homepage usa `title.absolute` ou title completo sem template.

### P1 — Schema FAQ de suporte está definido, mas não é renderizado

**Impacto:** médio. A página `/suporte` tem perguntas úteis e schema FAQ pronto, mas a constante `supportFaqSchema` não é injetada em `<script type="application/ld+json">`. O build local retornou `ld=0` para `/suporte`.

**Recomendação:** inserir o script JSON-LD na página de suporte ou remover a constante para evitar falsa sensação de cobertura. Validar com Rich Results Test renderizado.

### P1 — Ausência de imagens OG/Twitter explícitas

**Impacto:** médio. Compartilhamentos em WhatsApp, LinkedIn, Facebook/X e prévias de buscadores podem ficar pobres ou inconsistentes. Hoje há logo SVG usado em schema, mas não há `openGraph.images`/`twitter.images` nas páginas auditadas.

**Recomendação:**

- Criar `/public/og/botinho-home.png` 1200x630.
- Criar variações por cluster: cidade, nicho, blog/material.
- Declarar no root e sobrescrever por páginas prioritárias:
  - homepage
  - `/conteudos`
  - principais LPs
  - materiais/checklists

### P1 — Descrições fora do padrão ideal

**Impacto:** médio. A descrição da homepage tem 275 caracteres, longa para snippet e social. Institucionais têm 60–77 caracteres, curtas e genéricas. Isso reduz CTR e clareza de intenção.

**Recomendação:** mirar 140–160 caracteres com promessa específica:

- Home: “Automatize links de afiliado no WhatsApp: monitore grupos, converta links de Shopee, Mercado Livre e Amazon e publique ofertas com controle.”
- Suporte: “Tire dúvidas sobre QR Code, grupos, credenciais, planos e logs do BOTinho para operar ofertas de afiliados no WhatsApp com segurança.”
- Quem somos: “Conheça o BOTinho, software do Espelha Grupos para afiliados que organizam grupos, links e envios de ofertas no WhatsApp.”

### P1 — Conteúdo programático com risco de similaridade/doorway

**Impacto:** médio/alto em escala. Páginas por cidade e nicho são válidas, mas o template usa muitos blocos idênticos (`Hero`, `How`, `Features`, `Social`, `Pricing`, `FAQ`) e apenas blocos pequenos de diferenciação. Isso pode parecer doorway se a parte única for rasa.

**Recomendação:**

- Para cada cidade prioritária, adicionar 2–3 blocos exclusivos: sazonalidade local, exemplos de grupos/segmentos, calendário comercial local, objeções locais.
- Para cada nicho, adicionar exemplos reais de copy, checklist de credenciais, riscos por categoria, plataformas mais comuns.
- Priorizar 10 páginas com melhor potencial em vez de expandir volume sem profundidade.
- Medir indexação e impressions por cluster antes de criar novas páginas.

### P1 — Falta de breadcrumbs visíveis e schema consistente em todas as páginas públicas

**Impacto:** médio. Algumas LPs têm BreadcrumbList apenas para `lpType === 'pain'`; nichos orgânicos têm BreadcrumbList; blog/artigos nem sempre têm breadcrumb schema. Breadcrumb visível ajuda rastreamento, UX e contexto semântico.

**Recomendação:** criar componente `Breadcrumbs` público reutilizável e schema compartilhado para:

- `/conteudos`
- `/blog/*`
- `/materiais/*`
- LPs programáticas
- páginas institucionais

### P2 — `metadataBase` usa sempre produção, sem proteção contra staging

**Impacto:** baixo/médio. Em staging, gerar canonicals absolutos para produção pode ser aceitável se staging estiver bloqueado, mas pode confundir validações e previews. O projeto já tem `getSiteUrl()` com env, mas o root metadata fixa `https://espelhagrupos.com.br`.

**Recomendação:** usar `getSiteUrl()` também no root metadata ou documentar que staging sempre canoniza produção. Se staging for acessível publicamente, adicionar `noindex` por ambiente em staging.

### P2 — HTTPS e domínio público precisam de validação fora deste ambiente

**Impacto:** alto se confirmado. O `curl` deste ambiente recebeu 403 por túnel/envoy ao tentar `http://espelhagrupos.com.br` e `https://espelhagrupos.com.br`, então não foi possível validar redirects HTTP→HTTPS, HSTS, certificado, cache e headers reais. A homepage pública abriu via ferramenta web, mas headers não foram confiavelmente inspecionados daqui.

**Recomendação:** validar em ambiente externo real:

```bash
curl -I http://espelhagrupos.com.br/
curl -I https://espelhagrupos.com.br/
curl -I https://espelhagrupos.com.br/robots.txt
curl -I https://espelhagrupos.com.br/sitemap.xml
```

Critérios:

- HTTP deve redirecionar 301/308 para HTTPS.
- HTTPS deve responder 200.
- `robots.txt` e `sitemap.xml` devem responder 200.
- Considerar HSTS depois de confirmar HTTPS estável.

## On-page e conteúdo

### Homepage

**Forças:** proposta clara, estrutura por funcionamento/recursos/planos/FAQ, schema robusto, linguagem alinhada a afiliados e WhatsApp.

**Problemas:** descrição longa demais, promessa social com números fortes (“1.200+”, “R$4,2M”, “380k”, “4,9★”) deve ser sustentada por evidência pública ou removida/qualificada; ausência de OG image; CTA leva para login no contexto de SEO, mas poderia ter rota de cadastro/landing dedicada com tracking claro.

**Melhorias:**

- Criar bloco “Para quem é / Para quem não é” para reduzir leads ruins e aumentar confiança.
- Adicionar seção “Plataformas suportadas” com links internos para páginas específicas: Shopee, Mercado Livre, Amazon, Magalu.
- Adicionar FAQ sobre conformidade/risco de banimento, LGPD e consentimento.
- Criar comparação: “BOTinho vs copiar e colar manualmente”.

### Hub `/conteudos`

**Forças:** organiza blog, materiais e trilhas; possui CollectionPage/Breadcrumb/FAQ; bom para arquitetura.

**Melhorias:**

- Adicionar links para todos os clusters de LPs relevantes, não só dois nichos.
- Criar filtros por intenção: iniciante, afiliado, admin de grupos, escala.
- Adicionar “última atualização” visível por card, não só no hub.
- Incluir uma introdução curta para cada cluster com palavra-chave alvo.

### Blog e materiais

**Forças:** artigos têm Article schema em boa parte, alguns têm FAQPage, e o conteúdo é prático.

**Problemas:** poucos artigos para sustentar autoridade; ausência de author page/credenciais; ausência de datas published/modified em schema; alguns artigos não têm FAQ schema; poucos links internos para LPs de conversão.

**Melhorias:**

- Padronizar Article schema com `datePublished`, `dateModified`, `author`, `publisher.logo` e `mainEntityOfPage`.
- Criar autor institucional com bio e experiência operacional.
- Adicionar blocos “próximo passo” apontando para `/login?mode=register` e páginas de materiais.
- Criar calendário editorial por clusters:
  - conversão de links de afiliado
  - operação segura no WhatsApp
  - métricas/logs
  - nichos de ofertas
  - comparativos e alternativas

### Páginas por cidade

**Crítica:** são úteis para capturar buscas locais, mas a intenção “espelhar grupos WhatsApp em São Paulo” pode ser fraca/baixa. O valor SEO real pode vir mais de operações locais e nichos (“grupos de ofertas em São Paulo”, “divulgar ofertas no WhatsApp em SP”).

**Melhorias:**

- Reposicionar títulos para intenção mais natural: “Automação de ofertas em grupos de WhatsApp em São Paulo”.
- Adicionar casos de uso locais: bairros, eventos, datas comerciais.
- Não escalar para dezenas de cidades sem Search Console confirmando impressões.

### Páginas por nicho

**Crítica:** têm maior potencial que cidades porque conectam dor + categoria de oferta. Porém precisam de exemplos específicos por nicho para fugir de template genérico.

**Melhorias:**

- Supermercado: calendário semanal, vencimento de promoções, preço/estoque.
- Farmácia: compliance, restrições de produtos, cuidado com claims de saúde.
- Eletrônicos: preço histórico, garantia, marketplace confiável.
- Moda/beleza: sazonalidade, imagens, grade/tamanho.
- Cursos/infoprodutos: regras de afiliado, prova social, reembolso.

## Critérios de pronto para SEO técnico

Uma URL pública prioritária só deve ser considerada pronta quando:

- retorna 200;
- está no sitemap se e somente se for indexável;
- não é bloqueada no robots;
- tem canonical para si mesma;
- tem title único sem duplicação de marca;
- tem description útil;
- tem H1 único;
- tem links internos de entrada e saída;
- tem schema válido quando aplicável;
- tem OG/Twitter image;
- foi validada em build local e staging.

## Observações de risco operacional

- Não alterar portas, deploy, `.env`, banco ou PM2 para resolver SEO de conteúdo.
- Mudanças de metadata/layout no dashboard podem afetar client components; validar em staging antes de produção.
- Mudanças em `robots.txt`/sitemap podem ter efeito de indexação; revisar intenção de cada rota antes de publicar.
- Claims comerciais e números de prova social devem ter fonte real. Sem evidência, é melhor trocar por linguagem qualitativa.
